Architecture Lean Core & Plugin-First

LCMS Core — Documentation Technique

LCMS Core est un système de gestion de contenu fondé sur Laravel 11/12 conçu selon le paradigme Plugin-First. Le noyau n'héberge aucune logique métier : l'intégralité des fonctionnalités éditoriales (pages, navigation, médiathèque, méta-tags SEO) est portée par des extensions autonomes régies par des contrats publics et un ordonnancement topologique strict.

CMS Monolithiques Traditionnels

Modèles de données rigides codés en dur dans le noyau (articles, pages, boutiques forcés). Fort couplage horizontal entre extensions menant aux régressions silencieuses.

Approche LCMS Core

Noyau minimaliste d'infrastructure technique pure. Extensions totalement isolées, migrations indépendantes, résolution déterministe des dépendances et bus de hooks priorisé.

1 Installation Rapide (Packagist)

La méthode officielle recommandée pour démarrer un nouveau projet est d'utiliser Composer avec le template de projet Packagist. 

# Créer une nouvelle instance de LCMS Core
composer create-project elouafidev/lcms-core mon-site-lcms

# Accéder au dossier du projet
cd mon-site-lcms

# Démarrer le serveur local
php artisan serve
Automatisation complète : Composer génère automatiquement le fichier .env, calcule la clé applicative APP_KEY, crée la base de données SQLite (database/database.sqlite), applique les migrations du noyau et initialise le compte Super Administrateur racine.

2 Prérequis & Démarrage

Moteur PHP PHP 8.2 ou 8.3 avec extensions sqlite3, zip, curl, mbstring.
Gestionnaire Composer Composer 2.x pour le chargement dynamique PSR-4 des extensions.
Base de Données SQLite (par défaut en développement), compatible MySQL et PostgreSQL.

Identifiants par défaut du Super Administrateur

URL d'accès :http://localhost:8000/login ou /admin
Email :admin@lcms.local
Mot de passe :Password123!
Réinitialisation CLI :php artisan db:seed --class=UserSeeder

3 Architecture Globale & Monolithe Modulaire

LCMS Core adopte une séparation stricte en 3 couches distinctes, garantissant l'intégrité du noyau et l'indépendance de chaque composant :

1. Le Noyau Minimal (Lean Core — app/Core/)

Démarrage système, injection de dépendances IoC, validation stricte de manifestes JSON, tri topologique des dépendances, registre dynamique de navigation, tolérance aux crashs et bus d'interception (Hooks).

2. Le Panneau d'Administration Système (platform/core/)

Layout d'administration unifié sous AdminLTE 4 et Tailwind CSS (core::admin.layouts.app), persistance inaltérable de la barre latérale sombre, contrôle d'authentification et gestion visuelle du cycle de vie des extensions et thèmes.

3. Les Extensions Autonomes (platform/plugins/*)

Unités fonctionnelles étanches possédant leur propre espace de noms PSR-4, migrations isolées, modèles Eloquent, routes, contrôleurs et seeders dédiés.

Contrats Publics Stricts (`app/Core/Contracts`)

Pour préserver l'isolation logique, deux plugins ne communiquent jamais directement entre leurs implémentations privées. Tout échange de service s'opère via les interfaces publiques définies dans le Core :

Interface Rôle & Responsabilité
PluginInterface Contrat de base définissant l'identifiant, le nom, la version et le cycle de vie du plugin.
PluginManifestInterface Contrat d'accès immuable aux métadonnées validées du fichier plugin.json.
HookSubscriberInterface Permet à un plugin de déclarer ses écouteurs d'actions et de filtres sur le bus d'interception.
ThemeInterface Contrat pour le moteur de présentation et la hiérarchie de surcharge de vues Blade.
MediaStorageInterface Contrat d'abstraction du stockage de fichiers (implémenté par lcmscore.media-library).

Résolution Topologique des Dépendances (Algorithme de Kahn)

Lors du démarrage de l'application, le composant DependencyResolver ordonnance les plugins actifs selon un tri topologique déterministe fondé sur l'algorithme de Kahn :

Détection Préventive des Cycles

Si le plugin A dépend de B et B dépend de A, une exception typée CircularDependencyException est immédiatement levée, évitant tout blocage mémoire infini.

Gardes de Dépendances Inverses

Avant de désactiver ou désinstaller un plugin (ex: media-library), le noyau vérifie via getDependents() si d'autres plugins actifs en dépendent pour bloquer l'action destructrice.

Système de Hooks (Actions & Filtres)

Le bus de hooks (HookManager / façade Hook) permet aux extensions de modifier le comportement ou le rendu du CMS sans modifier le code source :

Filtres (`Hook::filter`)

Transforme une valeur ou un flux HTML à travers une chaîne priorisée de souscripteurs :

// Injection de métadonnées dans la balise <head>
Hook::addFilter('cms.head', function ($html) {
    return $html . '<meta name="author" content="LCMS">';
}, priority: 10);

// Déclenchement dans le template Blade
{!! Hook::filter('cms.head', '') !!}

Actions (`Hook::action`)

Déclenche des événements d'exécution sans attendre de valeur de retour :

// Déclenchement lors d'une action
Hook::action('cms.page.published', $page);

// Écouteur abonné dans un plugin
Hook::addAction('cms.page.published', function ($page) {
    Log::info("Page publiée : " . $page->title);
});

Résilience & Mode de Secours (Emergency Safe Mode)

LCMS Core garantit la disponibilité ininterrompue de la plateforme même en cas de panne critique d'un plugin défaillant :

Mise en Quarantaine Automatique

Si le ServiceProvider d'une extension déclenche une exception non interceptée au boot, elle est isolée en base (table cms_plugin_errors) et désactivée sans impacter les autres modules.

Bypass CLI d'Urgence

En cas d'incident bloquant l'accès Web, la commande php artisan cms:recovery:safe-mode --on neutralise le chargement de toutes les extensions pour rétablir l'accès admin racine.

4 Guide Développeur : Créer un Plugin

Chaque extension réside dans un sous-répertoire isolé sous platform/plugins/{vendor}.{nom}/ et suit une structure de type package Laravel PSR-4 : 

platform/plugins/lcmscore.mon-plugin/
├── plugin.json                 # Manifeste JSON validé obligatoirement
├── database/
│   ├── migrations/             # Migrations isolées (table cms_plugin_migrations)
│   └── seeders/                # Données initiales (exécutées via cms:plugin:seed)
├── resources/
│   ├── assets/                 # CSS/JS publiés vers public/vendor/plugins/{id}/
│   └── views/                  # Vues Blade (surchargeables par le thème actif)
├── routes/
│   ├── web.php                 # Routes Web (montées uniquement à l'état ACTIVE)
│   └── api.php                 # Routes API
└── src/
    ├── Http/Controllers/       # Contrôleurs du plugin
    ├── Models/                 # Modèles Eloquent isolés
    └── Providers/              # ServiceProviders enregistrés au boot

Le Manifeste `plugin.json`

Le manifeste est le document contractuel immuable inspecté par ManifestValidator (protection anti-traversée de répertoire, schéma JSON strict) : 

{
    "id": "lcmscore.mon-plugin",
    "name": "Mon Extension Métier",
    "version": "1.0.0",
    "description": "Exemple d'extension autonome pour LCMS Core",
    "author": {
        "name": "Équipe de Développement",
        "email": "dev@mon-domaine.com"
    },
    "compatibility": {
        "php": "^8.2",
        "cms": "^1.0"
    },
    "autoload": {
        "psr-4": {
            "Plugins\\MonPlugin\\": "src/"
        }
    },
    "providers": [
        "Plugins\\MonPlugin\\Providers\\MonPluginServiceProvider"
    ],
    "dependencies": {
        "lcmscore.media-library": "^1.0"
    },
    "conflicts": [],
    "routes": {
        "web": "routes/web.php"
    },
    "permissions": [
        {
            "key": "mon_plugin.manage",
            "label": "Gérer Mon Plugin"
        }
    ]
}

Exemple Pas-à-Pas : Création d'un Plugin

Étape 1 : Le ServiceProvider du Plugin

Déclarez les routes, les vues Blade et injectez l'entrée dans la barre latérale admin :

namespace Plugins\MonPlugin\Providers;

use App\Core\Admin\NavigationRegistry;
use Illuminate\Support\ServiceProvider;

class MonPluginServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Enregistrement des services IoC propres au plugin
    }

    public function boot(NavigationRegistry $navigation): void
    {
        // Chargement des vues Blade sous l'espace de noms mon-plugin::
        $this->loadViewsFrom(dirname(__DIR__, 2).'/resources/views', 'mon-plugin');

        // Ajout d'une entrée dans la barre latérale AdminLTE de LCMS Core
        $navigation->registerItem(
            id: 'mon-plugin-manage',
            label: 'Mon Plugin',
            url: '/admin/mon-plugin',
            icon: 'bi bi-stars',
            priority: 40,
            pluginId: 'lcmscore.mon-plugin'
        );
    }
}

Migrations & Seeders Isolés

Chaque extension possède son propre dossier database/migrations/ et database/seeders/. La gestion de persistance suit des règles précises :

Cycle des Migrations

  • À l'activation : les migrations en attente sont jouées dans une transaction.
  • À la désactivation : les tables et données sont strictement préservées.
  • À la suppression : possibilité de purger complètement les données via rollback.

Exécution des Seeders

Les seeders de plugins sont découverts et exécutés automatiquement via le moteur PluginSeederManager :

# Seeder un plugin précis
php artisan cms:plugin:seed lcmscore.mon-plugin

# Seeder tous les plugins actifs
php artisan cms:plugin:seed --all

Publication d'Assets & Installation ZIP Sécurisée

Les assets publics situés dans resources/assets/ sont publiés automatiquement dans public/vendor/plugins/{id}/ via la commande : 

php artisan cms:plugin:publish-assets lcmscore.mon-plugin --force

Protection contre les Attaques Zip Slip lors du Téléversement

Le pipeline PluginZipInstaller vérifie chaque chemin d'archive avant extraction : rejet formel de tout segment parent (..), des chemins absolus, et interdiction stricte de tout fichier exécutable binaire (.exe, .sh, .phar, .bat).

5 Moteur de Thèmes & Surcharge Blade (View Overriding)

Le système de présentation de LCMS Core permet de redéfinir l'apparence des pages publiques et des vues de plugins sans jamais modifier le code source de ces derniers : 

platform/themes/default-modern/
├── theme.json                  # Manifeste du thème
├── resources/
│   ├── assets/css/theme.css    # Styles compilés publiés vers public/vendor/themes/{id}/
│   └── views/
│       ├── layouts/app.blade.php
│       └── plugins/            # Surcharges des vues de plugins
│           └── lcmscore.pages/
│               └── page.blade.php  # Surcharge la vue du plugin de pages
Hiérarchie de Résolution Blade : Lorsqu'une vue est appelée, ThemeManager inspecte en priorité le dossier platform/themes/{theme-actif}/views/plugins/{plugin-id}/*. Si aucune surcharge n'est définie, la vue originale de l'extension est utilisée en repli transparent.

6 Administration Système, Sécurité & Paramètres

LCMS Core intègre un module complet d'administration dédié à la gestion des préférences, de la sécurité d'accès, du contrôle des rôles et des mises à jour applicatives. Conçu selon les principes de sécurité defense-in-depth, ce module offre un contrôle granulaire tout en préservant l'isolation stricte du noyau minimal.

Profil Utilisateur & Double Facteur (TOTP RFC 6238)

Accessible via /admin/settings/general, l'espace profil permet à l'administrateur connecté de mettre à jour son identité, de modifier son adresse e-mail avec validation d'unicité, de renouveler son mot de passe avec exigence de confirmation de l'ancien, et d'invalider ses autres sessions actives via Auth::logoutOtherDevices().

Stockage Cryptographique & QR Autonome

Les clés secrètes TOTP et codes de récupération sont chiffrés au repos via le casting Laravel encrypted. Le QR Code est généré localement au format SVG vectoriel pur, sans aucun appel externe (100% hors-ligne, zéro fuite de métadonnées vers des services tiers).

Validation Obligatoire & Codes de Secours

L'activation n'est effective qu'après la validation d'un premier code TOTP à 6 chiffres. 8 codes de secours d'urgence sont délivrés pour pallier la perte d'appareil, consommés de manière destructive à chaque utilisation et protégés contre les attaques par force brute (Rate Limiting).

Paramètres du Site, Passerelle SMTP & Mode Maintenance (503)

Le gestionnaire SettingManager centralise la persistance clé-valeur typée en base de données (settings) avec mise en cache automatique et invalidation instantanée lors des mutations : 

// Injection de SettingManager dans les services ou contrôleurs
$settings = app(\App\Core\Settings\Services\SettingManager::class);

// Lecture typée avec valeur par défaut de repli
$siteName    = $settings->get('site_name', 'LCMS Core');
$maintenance = (bool) $settings->get('site_maintenance', false);

// Écriture atomique et synchronisation du cache
$settings->set('site_name', 'Mon Portail LCMS');

Passerelle SMTP & Test Direct

Configuration des serveurs de messagerie (hôte, port 25/465/587, TLS/SSL, identifiants chiffrés). Le service MailTesterService déclenche l'envoi d'un e-mail de diagnostic (SmtpTestMail) en direct depuis l'administration pour valider la connectivité réseau et les identifiants sans quitter l'interface.

Mode Maintenance & Admin Bypass

Le middleware CheckMaintenanceMode intercepte toute requête publique avec une réponse HTTP 503 et la vue dédiée resources/views/errors/503.blade.php. Les administrateurs authentifiés ainsi que toutes les routes /admin/* bénéficient d'un contournement (Bypass) pour administrer et désactiver la maintenance sans interruption.

Contrôle d'Accès Basé sur les Rôles (RBAC)

Le système RBAC de LCMS Core offre une séparation stricte des privilèges via une matrice de rôles et de permissions relationnelles (roles, permissions, permission_role, role_user).

Rôle Système Identifiant Périmètre & Permissions Accordées
Super Admin super_admin Privilèges complets absolus. Immunisé contre la suppression et la perte de droits critiques.
Administrateur admin Gestion des extensions, thèmes, utilisateurs et paramètres système globaux.
Éditeur editor Gestion des contenus éditoriaux et consultation des extensions autorisées.
Utilisateur user Compte membre standard avec accès en lecture seule ou périmètre restreint.
Permissions Granulaires du Noyau : manage_plugins, manage_themes, manage_roles, manage_users, manage_settings, manage_updates. L'autorisation s'opère directement via les directives Blade @can('manage_plugins') ou les middlewares de routes Laravel can:manage_settings.

Gestion des Comptes & Révocation de Session

L'interface /admin/settings/users offre une console d'administration complète des comptes utilisateurs avec filtrage dynamique, pagination et indicateurs d'état de sécurité :

  • Création & Affectation : Attribution d'un rôle système ou sur-mesure dès la création du compte.
  • Bascule Actif / Inactif : La désactivation d'un compte révoque instantanément toutes ses sessions actives en base de données et bloque toute tentative de reconnexion ultérieure.
  • Réinitialisation Administrative 2FA : En cas de perte du terminal TOTP ou des codes de secours par un collaborateur, un administrateur habilité peut réinitialiser le second facteur du compte ciblé en un clic.

Moteur de Mises à Jour Core par Archive ZIP

Le service CoreZipUpdater permet de mettre à niveau le CMS directement depuis l'interface d'administration (/admin/settings/updates) sans exiger d'accès SSH ni de commande Git en production : 

// Structure attendue d'un package de mise à jour ZIP
update-v1.1.0.zip
├── update.json                 # Manifeste de validation de version et checksums
└── files/                      # Fichiers de remplacement confinés au noyau
    ├── app/Core/
    ├── resources/
    └── database/migrations/
1. Confinement Strict Interdiction absolue de modifier .env, platform/plugins/, platform/themes/, storage/ ou database/database.sqlite. Rejet immédiat de tout chemin relatif suspect (Zip Slip).
2. Sauvegarde Préventive Le BackupService génère un snapshot complet horodaté dans storage/app/backups/ avant toute écriture sur le système de fichiers.
3. Rollback Automatique En cas d'exception durant l'extraction ou les migrations, l'état initial est restauré intégralement et l'incident consigné dans les logs d'audit.

7 Référence des Commandes Artisan `cms:*`

Commande Arguments / Options Description
cms:plugin:list — Affiche le tableau des extensions découvertes, leur statut et état d'activation.
cms:plugin:enable {id} Installe (si nécessaire), exécute les migrations et active une extension.
cms:plugin:disable {id} Désactive une extension tout en préservant ses tables et données en base.
cms:plugin:seed {id?} {--all} {--class=} Exécute les seeders d'une extension spécifique ou de tous les plugins actifs.
cms:plugin:publish-assets {id?} {--all} {--force} Publie les fichiers statiques de l'extension vers public/vendor/plugins/.
cms:theme:list — Liste les thèmes disponibles et identifie le thème actif.
cms:theme:activate {id} Active le thème spécifié pour le rendu public et publie ses assets.
cms:theme:publish-assets {id} {--force} Publie les assets du thème vers public/vendor/themes/.
cms:recovery:safe-mode {--on} {--off} Active ou désactive le mode de secours pour bypasser toutes les extensions.
cms:security:enable-2fa {email?} Génère un secret TOTP, affiche l'URI/QR code en console et provisionne la 2FA pour un compte via CLI.
cms:recovery:disable-2fa {email} Commande d'urgence pour désactiver immédiatement la 2FA d'un compte en cas de perte de terminal (CLI emergency bypass).
